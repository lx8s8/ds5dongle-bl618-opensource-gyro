# 双固件可行性核查

更新日期：2026-11-14。目标是在上游原版与本项目体感固件之间选择启动，分别保留设置，切换时不重新编译、不重复刷写主程序。

当前已有独立启动管理器、双副本状态和分区视图提交、实体按键选择、管理页切换协议、G2.4 软件进入入口，以及离线安装／恢复计划工具。LCTech FS 管理器与应用已本地编译，主机及模拟网页检查通过；**尚未写入设备或完成 ROM 启动、双向跳转与原版配置软件真机验收，不能作为已完成的双固件产品发布。**

## 容量与启动基础

当前信海 BL616 为 4 MiB Flash。仓库分区表中，`FW` 已声明两处地址：

| 区域 | 起始地址 | 最大长度 |
| --- | --- | --- |
| A | `0x10000` | `0x200000`（2 MiB） |
| B | `0x210000` | `0x168000`（1.40625 MiB） |

上游 v3.24 的 LCTech FS／HS 主程序均为 837248 字节，可放入 B 区；本项目主程序也能放入。容量可容纳两份当前镜像，但分区表中的 `mfg` 与 B 区重叠，不能把这段地址当作未经核查的空闲存储。

SDK 的 `bflb_boot2_update_ptable()` 能切换分区活动索引；[官方 OTA 示例](https://github.com/bouffalolab/bouffalo_sdk/blob/master/examples/wifi/sta/wifi_ota_by_http/README.md) 说明 Boot2 依据活动分区启动应用。这提供了 A/B 基础，不等于已经完成了独立双固件管理。

## 软件双向切换的缺口

切到未经修改的上游固件后，本项目的专用命令不再运行。公开 v3.18 源码的配置接口仅有设置、保存、保存重启等命令；目前未核实 v3.24 二进制存在可用的“选择另一个启动槽”命令。新原型因此改为独立第一阶段启动管理器，先于两个应用运行，并提供上电按键入口。运行上游时仍需要这个实体入口，不能声称原版已支持本项目的软件重启命令。

完整方案至少需要：

1. 验证当前 Boot2 对两个独立镜像的启动、校验、活动索引与失败恢复行为，确认不会将备用镜像搬移覆盖主镜像。
2. 为上游运行期间提供可靠返回入口，例如经过验证的按键启动选择器，或上游提供的切槽命令。自定义启动器需要单独开发和验收；不能仅由网页模拟出来。
3. 核对两版 SDK 的持久存储布局、配置结构与配对记录兼容性，必要时隔离两套设置，保留共用配对数据必须实测。
4. 分别记录每槽的来源、板型、版本、长度和哈希；更新只写目标槽，校验成功再切换。上游更新从其 Releases 下载原始包并验证，不要求重新编译。
5. 验证更新失败、断电、两槽之一损坏、软件重启和手动恢复路径。

“软件缓存两份镜像，选择后串口重刷”可以绕过源码缺失，但每次切换仍会刷写，达不到双槽直接切换的目标。当前不改动用户设备的 Boot2、分区表或备用槽；体感稳定性修复仅更新现有主程序。

源码未迁移的直接证据见 [上游作者回复](https://github.com/sqlCRT/ds5dongle-bl618-opensource/issues/10#issuecomment-5742496052)：二进制继续发布，源码暂缓更新。因此不能通过合并 v3.24 标签来获得修改上游切槽入口的源码。

## 两套数据与原配置软件的兼容范围

再次核查的具体证据：

- 本项目接收器设置用 `dongle_cfg`，普通映射使用各 profile 键及 `remap_prof`；蓝牙配对也经 `bt_settings_*` 进入同一 KV 后端。新增体感档使用独立键名，不代表普通设置和配对已经分成两套。
- 固定 SDK 的 [LittleFS 兼容后端](https://github.com/sqlCRT/bouffalo_sdk/blob/b3532953322194233f80436701e7fb6bb4ad8275/components/fs/littlefs/easyflash_port/lfs_easyflash.c) 将整套 KV 挂载到 `PSM`。已验证的设备回读里，PSM 为 `0x3E9000` 起的 32 KiB，含 LittleFS 标记；不能通过在网页多保存一份 JSON 来覆盖配对和未来上游未知设置。
- 现有 4 MiB 回读的有效分区表位于 `0xE000`，头和条目 CRC 均通过；FW 活动槽为 0，备用槽与 mfg 重叠。`0xF000` 副本未初始化。这里只读取既有回读文件，没有改写设备。
- 上游配置页面当前声明配置版本 3、34 字节，本项目基础配置为版本 2、29 字节。结构已有差异，不能假定共用 `dongle_cfg` 会自动保留各自设置。
- 对方页面 `0xF6 / 0x03` 的操作名为“重连 USB”；仅凭这一操作不能确认整颗芯片会经过自定义启动管理器，仍不能据此保证从原版软件无感返回。

目标方案保留未经修改的上游应用、原有 Sony 身份及 HID 配置协议，由独立启动管理器选择固件，并隔离每份固件的可写数据视图。末尾原型采用独立数据区域及原子分区视图提交，不在切换时复制整套存储；具体的 ROM 入口、跳转和两端兼容性仍待真机验证。不同固件重新配对后，控制器一侧保存的密钥也可能变化，不能仅保留接收器 Flash 就声称所有配对状态永远互通。

| 操作 | 双固件方案需要达到的行为／当前限制 |
| --- | --- |
| 原版模式下用原配置软件读取、修改、保存 | 应作用于原版自己的存储，原协议及设备身份保持；待实现后真机验收 |
| 切回体感模式 | 原型通过整套可写分区视图恢复自己的数据，主机测试通过，真机未验收 |
| 在运行中的原版直接点本工具切回 | 必须有独立返回入口；原版不执行本项目切换命令，当前无法保证纯软件单击完成 |
| 原配置软件或原刷机工具更新固件 | 需单独核查。写 Boot2、分区表或 OTA 备用槽可能覆盖双固件管理器或另一镜像，不能承诺任意原版升级工具完全不受影响 |
| 由本工具更新单个模式 | 需要只更新目标镜像并验证来源、板型、大小、哈希及保留区域，不能直接执行原版整片刷机配置 |

最近一次取轴与 FPS 视角复测只修改网页，不需要再次刷固件。真正安装双固件管理器则需要一次专门的安装／迁移，不能靠更新网页或重新刷当前 G2.3 主程序获得。当前只有实验原型，没有已完成硬件验收的双固件安装包。

### DS5DongleRE 的兼容边界

2026-11-14 检查 [NiceTimeJob/DS5DongleRE](https://github.com/NiceTimeJob/DS5DongleRE/tree/6f5035d) 的公开源码（版本 R3.28）。它是同一上游的独立分支，R3.28 不是 sqlCRT v3.24 的后续版本。其映射引擎将 `cfg.bin`、`gcal.bin` 和宏文件写入 `media` 分区的 LittleFS；本原型只为 PSM/KEY/DATA 提供双份视图，`media` 仍共用。因此当前原型**不支持承诺 DS5DongleRE 与另一固件的全部数据隔离**，接入前必须补充 media 存储规划及迁移、恢复测试。现有离线工具的镜像头检查也不能代替这项兼容性验收。

该项目固定模拟普通 DualSense（054C:0CE6），已移除 Edge USB 描述符；虽然仍能读取 Edge 扩展按键，但不满足本项目保留 DualSense Edge USB 身份的要求。它的映射配置协议也与本项目不同，不能直接用对方网页设置本项目固件。公开仓库未提供网页源码或 GitHub Releases；源码中也未找到用户可选的双固件管理实现。以上是源码检查结果，未向接收器刷入该项目。

## 当前原型的具体实现

这仍是 Flash 区域划分，和电脑上的磁盘分区无关。可以组合成一个安装包一次写入，但不能把未经修改的第三方程序当作本项目内部的一个功能开关；上游程序仍依赖它自己的代码、启动地址与存储协议。不限定烧录器品牌，具备相应地址、校验和数据迁移能力的工具都可以完成安装／恢复。

| 区域 | 地址／长度 | 用途 |
| --- | --- | --- |
| 独立管理器 | `0`／不超过 `0xE000` | 普通未加密 XIP 首阶段镜像，由 ROM 进入，替代原 Boot2；使用 SDK 的 RAM 内跳转函数进入选中的应用，待真机验证 |
| 分区表双副本 | `0xE000`、`0xF000` | 保留 SDK 格式，FW 与 PSM/KEY/DATA 的活动视图一起提交 |
| 体感应用 | `0x10000`／`0x200000` | 保留 Sony 身份，G2.4 增加软件进入管理器的命令 |
| 上游应用 | `0x210000`／`0x120000` | 原始应用二进制逐字节保留，不注入本项目 HID 命令 |
| 体感数据 | PSM `0x330000`，KEY `0x338000`，DATA `0x33A000` | 长度分别为 `0x8000`、`0x2000`、`0x5000` |
| 管理状态双副本 | `0x340000`、`0x341000`／各 4 KiB | 两个应用的版本、完整文件 SHA256、地址、容量、默认槽及一次性管理入口请求，CRC 和代数保护 |
| 上游数据、工厂参数 | 原地址保留 | 上游 PSM/KEY/DATA 位于 `0x3E9000` 起，factory `0x3F8000` 起保持原字节 |

旧 mfg 条目与备用镜像重叠，原型安装时移除；不能直接使用旧分区表。管理器只切状态和分区视图，不在每次切换时搬移应用或复制数据。启动时核对镜像 SHA256；缺失／损坏时留在管理接口，不盲跳。

原型的按键动作限定在**正常插电后的约 2 秒快闪窗口**：

- 不操作：启动记忆的模式。
- 短按一次 BOOT 并松开：选择另一个模式并启动。
- 在窗口内按住 BOOT 约 1 秒：停在管理接口，用控制中心选择模式。
- 按住 BOOT 再插电：仍由芯片 ROM 进入烧录模式，不能把这步描述成切模式。
- 应用已经启动后的原有单击、双击、长按功能不改写；当前 G2.3 也没有上述新启动窗口，不要在旧固件里长按尝试切模式。

管理页只请求 vendor 管理接口的 `0x70` Feature，不误连日常 PS 手柄接口。G2.4 的 `0xF6 / 4` 只在识别已安装管理器和有效状态时提交一次性进入请求，并复用原命令回执后重启；没有管理器时拒绝，不创建新分区。运行上游时，实体上电入口用于返回管理器。管理接口暂用私下测试 VID/PID，不能作为未经分配的公共产品身份发布。

## 安装与恢复工具

`scripts/dual_firmware_plan.py` 是开发用**离线计划工具**，不连接硬件、不执行烧录；当前网页也没有首次安装或卸载按钮。输入必须是本机接收器的完整 4 MiB 读取和匹配板型的镜像。文件大小、未加密 XIP 头、入口、CRC、有效载荷哈希及原布局会被检查；不接受任意板型、加密镜像或过大的新版上游程序。

```sh
bash scripts/build_boot_manager.sh
python3 scripts/dual_firmware_plan.py install \
  --snapshot current-4MiB.bin --upstream-snapshot previous-upstream-4MiB.bin \
  --manager dist/boot-manager/ds5-boot-manager-lctech616-fs-experimental.bin \
  --gyro firmware/lctech616/ds5dongle-lctech616.bin --upstream upstream.bin \
  --gyro-version G2.4 --upstream-version 3.24H --output private-install-plan
python3 scripts/dual_firmware_plan.py restore \
  --snapshot dual-current-4MiB.bin --original-snapshot original-4MiB.bin \
  --slot 1 --output private-restore-plan
```

不提供旧上游快照时，只能将安装时现有的数据复制为两套独立初值，不能找回过去已被覆盖的设置。提供的历史快照也必须来自同一接收器；首次真机安装需要读取当时的最新状态，不能直接刷历史验证计划。

每个计划包含原始读取、预期完整镜像、按序写入的差异扇区和哈希，第一阶段最后写入。**含配对密钥，只能留在用户本机，不能上传 Git 或 Releases。** 安装中断恢复和整个链路仍未真机验收；元数据原子提交测试不等于首次安装也已通过断电测试。

恢复单固件会恢复原始 Boot2 与两份原始分区表，把所选应用迁回 `0x10000`、所选数据迁回原地址，同时恢复原制造区。另一个模式的数据保留在恢复前的本机完整读取里。恢复完成后不再依赖启动管理器，可使用匹配板型的第三方常规刷机流程；只覆盖主程序 BIN 不等于卸载双固件，整片擦除会清空设置和配对。

当前验证：管理器约 52.5 KiB，G2.4 应用 787072 字节，上游 837248 字节。8726 个元数据／分区提交中断点、按键逻辑、写入范围、未安装拒绝和软件进入请求检查通过，ASan/UBSan 通过；离线安装／恢复测试 5 组、网页协议测试和 125 项模拟 UI 断言通过。历史真机读取的离线安装／恢复逐字节对照通过；**不等于已在硬件运行双固件**。分槽更新镜像、网页安装／卸载、原版配置软件兼容性和两端实际游戏仍待完成或验收。
